## 内核连接自愈（12:25–12:35）

**用户症状**：「UI 经常连接不到内核，能不能强绑定一下」+ 两张截图：通知栏「内核运行中 · 127.0.0.1:42083」，设置页「内核未连接」。

**关键判断**：内核进程是好的（通知栏就是 `KernelState.Ready` 驱动的），问题全在 UI 侧。

**根因是三层「一次性」叠加**：
1. `HttpCoreTransport.connect()` 只跑一次，`onFailure` 发个事件就永久放弃 —— 内核刚 bind 完、accept 未就绪的毫秒级窗口就足以打死
2. `connected` 只由 WS 的 `ready` 帧驱动，ready 帧缺席就永久显示未连接（哪怕消息能收发）
3. REST 是独立链路（独立 client + 独立 CookieJar），`KernelApi.init()` 也只试一次，失败则 `/api/config` 拉不到 → `kernelConfig` 为 null → 设置页显示未连接

**修法（6 个文件）**：
- `HttpCoreTransport`：`connect()` 改自愈循环（health 探活 → 取 Cookie → 连 WS → 挂起等断 → 退避 1/2/4/8s）；`connectOnce()` 返回「是否曾连上」，稳定 30s 后断才重置退避；`disconnect()` 不再 shutdown client
- `CoreTransport`：新增 `CoreEvent.Link(connected, attempt, retryInMs)`，与 `Ready` 分离，`onOpen` 即报连上
- `ChatViewModel`：Link 分支、`initKernelApi()` 重试 4 次、25s 超时自动 restart、`Banner.retryable`、`retryKernel()`
- `CoreService.restart()`：`startService` → `startForegroundService`（超时兜底时 Service 可能没起来）
- `AppRoot`：横幅加「重试」按钮
- `KernelSettingsSection`：「未连接」拆三态（测试模型 / 链路未通 / 已连但配置没读到）

**已记 AGENTS.md P-019**：连本地服务不能押注一次连接；判活要打业务端点（`/api/health`），只探 TCP 端口不够。

**出包**：release 58 MB（12:35），`compileDebugKotlin` 三次通过。

**未验证**：自愈循环的真实重连行为、退避节奏、Link(true) 后设置页是否显示配置。**未覆盖**：内核进程卡死（不退出也不响应）时自愈循环只会一直重试，需手动点「重试」踢进程。

## Android DNS 修复（21:47–22:00）

**报错**：`lookup api.deepseek.com on [::1]:53: connection refused`

**根因链**：内核 CGO_ENABLED=0（零依赖）→ 纯 Go 解析器只认 `/etc/resolv.conf` → **Android 没有这个文件** → 回退 127.0.0.1:53。传统补救 `net.dns1` 属性**现代 Android 已废弃**（实测为空），DNS 在 netd 里，只有 Java 的 ConnectivityManager 拿得到。

**试过但撤回**：CGO_ENABLED=1 + NDK 交叉编译（能编过）。**撤回原因**：cgo 与 fork 是 Go 的已知雷区（cgo callback 死锁），而这个内核大量 exec 子进程（cfrun/proot/apk）。且用户明确强调"零依赖的 Go 开发"。

**最终方案（零新增依赖）**：
- 内核 `pkg/netdns/netdns.go`：init 读 `CODEFORGE_DNS`，装自定义 Dial 的 `net.Resolver`
- 客户端 `CoreService.kt`：`ConnectivityManager` 取第一个 IPv4 DNS，注入 `environment()["CODEFORGE_DNS"]`
- **只取 IPv4**：IPv6 的 hostAddress 带 `%wlan0` 后缀，JoinHostPort 拼不合法

**Kotlin 坑**：helper 必须放顶层。`ProcessBuilder.apply {}` 里的 receiver 是 ProcessBuilder，访问外部类成员报 `Outer class ... cannot be used as receiver`。

**验证**：`/proc/<pid>/environ` 确认 `CODEFORGE_DNS=192.168.5.1` 注入成功；启动后无 DNS 横幅。探测按钮 adb 点不动（同一行"删除"也点不动），待人工确认。

## 「发送消息报解析失败」根因（23:20–23:45，静态分析）

**五环根因**：
1. **`state.yaml` 优先级高于 `local.yaml`**（`config.go:417`：Default→default→local→**state**→env）。手改 local.yaml 的 model 不生效。
2. **主界面选的模型是 Composer 局部状态** `pickedModel`（rememberSaveable），不落盘、不写内核，重启即丢。
3. **`syncModelToKernel` 读错源**：读 `state.modelName`（内核现状）而非 `AppSettings.llmModel`（用户意图）；且 600ms 时 ready 帧还没到，直接 return，再没机会跑。
4. **供应商 key 是空的**：`seedDeepSeekIfEmpty` 传 `keyValue=""`；模型继承供应商 → apply 失败。`ProviderInfo` 不返回 key（json:"-"），客户端判断不了。
5. **失败表现误导**：apply 失败 → state.yaml 保持 claude → 内核拿 DeepSeek base_url 请求 claude → 上游 404 → 客户端只报「数据格式不对」。

**修**：syncModelToKernel 改读 llmModel；预置带 llmApiKey；apply 前补写供应商密钥；apply 失败重启内核兜底。

**核心教训**：「界面显示」与「内核生效」是两套状态，唯一通路是 `/api/models/apply`，失败无任何可见反馈。
